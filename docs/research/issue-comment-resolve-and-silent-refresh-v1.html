① 背景与目标

用户三点诉求：

  • 评论解决：参考 multica web，在 Issue 评论里加「以此回复解决评论」按钮，把某条回复标记为该线程的已解决答案。
  • 后台刷新：支持后台刷新收件箱与 Issue 列表 / 详情。
  • 无感刷新：自动刷新不能把现有列表搞坏（清空、闪空、转圈）；只有手动下拉才允许转圈。
核心判断把「刷新」从「清空重建」改成「后台静默合并」，并补齐评论解决能力。两件事相互独立，可分别交付。

② 调研结论

评论解决：官方已确认

从 server 源码 server/internal/handler/comment.go 确认：

  • POST /api/comments/{id}/resolve 写 resolved_at/resolved_by_type/resolved_by_id；DELETE .../resolve 取消。
  • 单解决不变量：一个线程最多一条已解决评论；resolve 时同事务清掉同线程其它答案（ClearOtherThreadResolutions）。
  • 目标可为任意评论（根或回复），与 web v0.3.19 changelog「resolve a specific reply」「only one resolved answer at a time」一致。
  • 实时事件：comment:resolved / comment:unresolved。

官方 mobile 把菜单项注释成「root only」是过时的；server 实际支持任意评论 —— 这正是「以此回复解决」所需。

③ 方案 A：评论解决（以此回复解决评论）

对齐 server 语义：任意评论可解决、每线程单解、解决即替换。UI 上把「以此回复解决」做成回复上的一等动作，已解决线程折叠成一行。

A1 · 数据模型（Models.swift）

Comment 增加三个可空字段，snake_case CodingKeys，decodeIfPresent：

public let resolvedAt: Date?
public let resolvedByType: String?
public let resolvedByID: String?
// resolvedAt = "resolved_at" / resolvedByType = "resolved_by_type" / resolvedByID = "resolved_by_id"

A2 · API 客户端（APIClient.swift）

public func resolveComment(commentId: String, workspaceId: String? = nil) async throws -> Comment {
    try await request("POST", path: "api/comments/\(commentId)/resolve",
                      queryItems: workspaceQuery(workspaceId))
}
public func unresolveComment(commentId: String, workspaceId: String? = nil) async throws -> Comment {
    try await request("DELETE", path: "api/comments/\(commentId)/resolve",
                      queryItems: workspaceQuery(workspaceId))
}
注意server 的 DELETE 也返回更新后的 Comment。若现有 request 对 DELETE 默认按 EmptyResponse 解码，unresolveComment 必须显式按 Comment 解码，避免本地态漂移。

A3 · ViewModel（IssueDetailViewModel.swift）

  • CommentThread 加 var resolvedReply: Comment?（线程内 resolvedAt != nil 的那条，至多一条），displayedCommentThreads 计算时填充。
  • 解决动作：乐观翻转 → 调 API → 服务器权威值覆盖 → 失败回滚。
  • applyResolvedComment(_:) 按 id 替换进 commentLoader.items，并清掉同线程其它评论的 resolved 字段（单解不变量）。
  • 复用 threadRootCommentId(for:) 定位线程；删除已解决答案时线程自动回到未解决。
public func resolveComment(commentId: String) async {
    applyResolveOptimistic(commentId: commentId, resolved: true)   // 乐观：本条置 now，同线程其它清空
    do {
        let updated = try await api.resolveComment(commentId: commentId, workspaceId: resolvedWorkspaceId)
        applyResolvedComment(updated)                              // 服务器权威覆盖
    } catch {
        revertResolveOptimistic(); lastError = error              // 回滚
    }
}

④ 方案 B：无感后台刷新

B1 · 设计原则

  • 刷新 ≠ 清空。任何刷新都保留现有内容，新数据回来后就地合并/替换。
  • 两类加载状态分离：isLoading（首次/分页，允许 ProgressView 与空态）vs isRefreshing（后台静默，永不闪空、永不转圈）。
  • 只有手动下拉可转圈：.refreshable 走系统下拉转圈（覆盖层，不动内容）。自动刷新一律 silentRefresh()。
  • 保留用户上下文：合并时保留选中、折叠分组、滚动位置、已加载深页。

B2 · PaginatedLoader 增强（Core/Cache/PaginatedLoader.swift）

public var isRefreshing = false

/// 静默刷新第一页：拉 offset=0，就地替换/合并，保留更深分页。
/// 全程不触发 isLoading、不清空 items。
public func silentRefreshFirstPage(fetch: (Int) async throws -> PageResponse<T>) async throws {
    isRefreshing = true
    defer { isRefreshing = false }
    let page = try await fetch(0)
    let freshIds = Set(page.items.map { $0.id })
    let tail = items.filter { !freshIds.contains($0.id) }   // 保留首页外已加载深页
    items = page.items + tail
    offset = page.items.count
    hasMore = page.hasMore
}

reset() 仍保留，仅用于真正上下文切换（workspace 切换且需清空旧工作区数据时）。

B3 · 列表 ViewModel 改造

IssueListViewModel（按状态分组）

  • 新增 silentRefresh()：对每个 IssueStatus.listCases 并发拉首页，按 id 就地合并进 issuesByStatus（首页覆盖/插入，深页保留），重算 offsetsByStatus/pageHasMoreByStatus/loader.items。全程 isRefreshing=true，不调 resetPagination()。
  • refresh() 改为直接 silentRefresh()（下拉转圈由系统层提供，内容不清空）。
  • refreshIfIdle()（自动入口）改调 silentRefresh()，跳过条件改为「isRefreshing 时跳过」。
  • workspace 切换：单独保留 fullReset()，且「新数据到位再替换」消除空窗。

InboxViewModel

  • 新增 silentRefresh()：loader.silentRefreshFirstPage { api.listInbox(...) }，复用 deduplicateInboxItems。
  • refresh() 不再 loader.reset()；refreshIfIdle() 调 silentRefresh()。

B4 · Issue 详情改造（IssueDetailViewModel）

  • 新增 silentRefreshComments()：commentLoader.silentRefreshFirstPage { api.listComments(...) }，重算 displayedCommentThreads，不调 reset()。
  • loadComments()（首屏）保持现状；之后的刷新一律走静默路径。
  • Issue 本体 / timeline / active tasks / agent runs 加 silentRefresh*()，就地替换不切 isLoading。首版优先 comments + issue 本体 + timeline。

B5 · UI 状态机（不闪空、不转圈）

场景isLoadingisRefreshing展示
首次进入，无数据truefalse首屏 ProgressView
已有数据 + 自动刷新falsetrue原列表不变，无转圈
已有数据 + 下拉刷新falsefalse系统下拉转圈（覆盖层），内容不变
已有数据 + 空结果返回falsefalse保持原列表，不闪空态
首次加载失败falsefalse错误重试视图
关键空态判断必须同时要求 !isRefreshing 且「从未成功加载过」，否则后台刷新途中网络抖动返回空会把列表误判成空。

B6 · 实时补充（可选 · P2）

WebSocketActor 已具备 subscribe(to:)。第二阶段 Issue 详情订阅 comment/issue 事件、Inbox/列表订阅变更事件，做到「改动即同步」。第一阶段以「30s + 回前台静默刷新」达成无感即可。

B7 · 边界

  • 合并去重按 id，新值覆盖旧值字段；合并后按当前 sortOption/sortDirection 重排，避免顺序抖动。
  • 合并只替换数据，不动 selectedIssueIds / collapsedStatusSections。
  • 首页刷新若 hasMore 变化，重置对应状态游标；深页条目按 id 保留，下次「加载更多」从新 offset 继续。
  • silentRefresh 失败只记 lastError（可选轻提示），不回滚已有列表（没清空过）。

⑥ 风险与回滚

  • 合并语义回归：去重/排序不当会丢条目或跳动。对策：合并单元加单测（按 id 合并、保留深页、稳定重排）；灰度先 Inbox 再 Issue 列表。
  • DELETE 解码漂移：unresolveComment 误用 EmptyResponse 会与 server 不一致。对策：显式按 Comment 解码，以服务器返回为权威。
  • 单解不变量破坏：乐观更新需同步清同线程旧答案；单测覆盖「resolve 第二条 → 第一条被清」。
  • 性能：静默刷新不改首屏路径，额外成本仅一次首页请求（与现状同频），无新增轮询。
  • 回滚：P0/P1 相互独立；P0 出问题可回退 refresh() 清空路径（退回现状，无数据风险）；P1 出问题可隐藏菜单项，不影响阅读。

⑦ 验收清单

  • 自动刷新（30s / 回前台）时 Inbox 与 Issue 列表不闪空、不转圈、滚动位置不跳。
  • 手动下拉刷新显示系统转圈，松手后内容更新。
  • workspace 切换无空窗（新数据到位再替换）。
  • Issue 详情评论后台刷新不清空已有评论。
  • 任意回复可点「以此回复解决」，徽标立即出现（乐观），失败回滚。
  • 同线程解决第二条时，第一条自动取消解决（单解）。
  • 已解决线程折叠为一行，可展开、可跳到答案。
  • 「取消解决」可还原线程。
  • en / zh-Hans 文案齐全；解决按钮有 accessibilityIdentifier。
